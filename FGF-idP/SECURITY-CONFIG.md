# HTTP deployment configuration

Build and test with Go 1.26.8 (the repository toolchain). Dependencies require Go 1.26.0 or newer.

`CORS_ALLOWED_ORIGINS` is a comma-separated list of exact browser origins, for example `https://portal.example.com,https://admin.example.com`. Include the port when nonstandard. Credentials are enabled only for allowed cross-origin requests. Empty or unset means same-origin only; requests without an Origin header still work. Wildcards, paths, user information, query strings, fragments and malformed entries abort startup. CORS is a browser policy, not authentication or CSRF protection. Cookie SameSite/Secure rules still apply.

`TRUSTED_PROXIES` is a comma-separated list of reverse-proxy IP addresses or CIDR ranges, for example `127.0.0.1,::1,10.20.0.0/24`. Empty or unset trusts no proxy: forwarded IP headers cannot change the client IP used for logging and rate limiting. Invalid entries abort startup. Configure only actual proxy peers; never use universal CIDRs. Restrict direct network access and have the proxy overwrite client-supplied forwarding headers. Terminate HTTPS at that proxy.

The HTTP server uses a 5-second header-read timeout, 15-second request-read timeout, 30-second response-write timeout and 60-second keep-alive idle timeout. These are fixed defaults in `main.go`. Interrupt or SIGTERM stops accepting connections and gives active requests up to 10 seconds to finish, then closes remaining connections. Allow more than 10 seconds in the deployment termination grace period. Auth cleanup receives the same cancellation context.

`GET /health/live` returns 200 while HTTP is serving, independently of database availability. `GET /health/ready` returns 200 when the application's SQL connection pool responds to PingContext, or 503 when the ping fails; it uses the request context with a two-second deadline. Probes require no authentication and bypass the auth groups' rate limiter. They return only status, not database errors. Use readiness to direct traffic and liveness to detect process failure.

Auth requests expire after 10 minutes and authorization codes after 5 minutes. Both are stored in the configured SQL database; codes are consumed atomically after client, redirect and PKCE validation. Expired requests, codes and token revocations are removed at startup and every minute. Reads reject expired state even between cleanup runs. SQLite persists across restarts when SQLITE_PATH names a durable file; in-memory SQLite does not. Multiple instances must use the same PostgreSQL database, issuer, signing key and signing key ID, and session/HMAC secrets. Cleanup runs on each instance safely. Existing in-memory authorizations from the previous build cannot migrate; those users must restart authorization once.

Logout revokes the bearer access token and/or session cookie supplied with the request, using SHA-256 fingerprints retained until token expiry. Session authentication and UserInfo check the shared revocation table; database errors fail closed. Revocation survives restarts and node changes. A new random JWT ID keeps a new login distinct from a revoked token issued in the same second. Logout does not revoke other tokens that were not supplied, and external resource servers validating JWTs offline do not see this database; they must enforce revocation separately or honor short access-token lifetimes.

Validation used Go 1.26.8: go test ./..., go vet ./..., and govulncheck. The scan reports zero reachable vulnerabilities and zero vulnerable imported packages. It still lists GO-2026-5932 at the module level for the unused, unmaintained x/crypto/openpgp package; this application does not import it. PostgreSQL deployment integration must be verified against the operator's database; the automated persistence and concurrency tests use SQLite.

Email verification bindings are consumed atomically before trusting a device or issuing a session. Verification tokens include a random nonce; failed sends clear only their own binding. Redundant user-table verification storage is no longer used (existing columns are not dropped automatically). JWT parsing requires canonical base64url encoding so equivalent signature encodings cannot bypass fingerprint-based revocation.

The Windows environment could not run go test -race because CGO is disabled and a configured C compiler is unavailable. Concurrency regressions still exercise simultaneous code redemption and verification-link replay. Linux cross-compilation succeeds.

The Go executable now embeds the production /login page and its local assets. Leave FRONTEND_BASE_URL unset for same-origin login; existing external login overrides are retained. JSON clients can explicitly request application/json on POST /x/login and receive redirect_to instead of an HTTP redirect. Browser verification failures use a fixed error code on the login page; API clients retain JSON responses. Login HTML and credential responses use no-store; the page applies a self-only content security policy and no-referrer policy. The browser stores no passwords or tokens. Configure real SMTP delivery before enabling production first-device login; the isolated browser fixture skips real delivery.

The legacy web tester and its cookie-editing routes are not part of the production executable. The loopback browser fixture's /test routes only compile in Go tests. Do not expose the development tester on the production origin.

The admin console at /admin and its API under /x/admin are deliberately excluded from CORS_ALLOWED_ORIGINS: middleware.CORS enables credentials for every allowed origin, which would let a listed origin drive the console with an operator session cookie. The API is same-origin only and relies on SameSite=Lax cookies, the absence of CORS, an application/json content-type requirement on mutations, and the fact that no mutation is reachable by GET. Do not add a GET-shaped mutation route under /x/admin. Console sign-in is POST /x/admin/login, independent of the OAuth flow; a wrong password, an unknown account and an insufficient role return an identical 401 so administrator accounts cannot be enumerated. A correct password on a device the user has not verified by email returns 203 and a verification link bound to that device; the console API rejects any request without a verified device cookie (401 device_verification_required), so a session obtained through the OAuth login cannot open the console before its device is verified either. Permission levels are read from the database on every request because a session cookie lives for 30 days and revocation is keyed by token hash, not by user: a demoted or deleted account loses access on its next request.

OAuth client registration is restricted to role 6 (root) because a redirect URI is sufficient to collect authorization codes for every user. Registered redirect URIs must be absolute http or https URLs with a host, no fragment (RFC 6749 3.1.2) and no wildcard, at most ten per client and 512 bytes each; outside DEBUG mode https is required except for localhost, 127.0.0.1 and [::1]. Matching stays byte-for-byte, so stored values are only trimmed and de-duplicated, never path-normalized. Grant and response types are fixed to authorization_code and code. Client secrets are stored as bcrypt hashes and the plaintext is returned exactly once, at creation and at rotation; it cannot be recovered afterwards. Deleting a client is a soft delete that immediately removes it from /x/auth and /x/userinfo, and its client_id cannot be reused. When DEBUG and ALLOW_INSECURE_DEFAULT_CLIENT are both off, startup logs an error for every client that still accepts an empty secret, including the seeded fgf-mc-panel; it warns rather than refusing to boot so existing deployments can upgrade.
